## 1. 목적과 성공 기준

**목적**: 일반 사용자에게 공개하는 웹 서비스(PWA). 해외여행 외화 지출을 기록하고, 결제수단별 실제 환율·수수료를 반영해 "환율 때문에 손해 보는 사람이 없는" 정산 결과를 보여준다.

**MVP 성공 기준**
1. 가입 없이 여행을 만들고, 초대 링크로 들어온 사람이 멤버를 골라 바로 지출을 입력할 수 있다.
2. 원본 명세 §12의 시나리오 3개가 직관과 맞는 결과를 낸다 (테스트로 고정).
3. 모든 정산 결과의 순잔액 합계가 정확히 0이다 (원 단위 오차 없음).
4. 정산 결과가 송금 목록으로 나오고, 각 항목에 **원화 금액 + 여행 평균 환율 기준 외화 + 오늘 환율 기준 외화**가 함께 표시된다.
5. 다른 여행의 데이터는 읽을 수도, 쓸 수도 없다 (RLS 테스트 통과).
6. Vercel + Supabase에 배포되어 외부에서 접속할 수 있다.

### 2.1 환율 데이터 소스

2026-10-12에 확인한 내용:
- Frankfurter(ECB): 30개 통화. KRW·JPY·CZK·CHF·THB는 있지만 **TWD·VND가 없다** → 원본 명세 시나리오 2(대만)를 처리할 수 없다.
- ExchangeRate-API Open Access(`open.er-api.com/v6/latest/KRW`): 키 없이 166개 통화, 하루 1회 갱신. 출처 표기가 의무이고, 과거 날짜 조회는 지원하지 않는다.
- 한국수출입은행 API: 원화 기준 공식 고시 환율이다. 다만 TWD·VND 포함 여부는 확인하지 못했다(인증키 발급 후 `cur_unit` 목록 확인).

**결정**
- `RateProvider` 인터페이스 뒤에 공급자를 숨긴다. 우선순위는 **① 한국수출입은행(지원 통화일 때) → ② ExchangeRate-API Open Access**이다.
- Vercel Cron이 **하루 1회** 여행에서 쓰이는 통화 전체의 환율을 받아 `exchange_rates`에 쌓는다. 과거 날짜 조회 API가 없으므로, 우리 표에 쌓인 값이 곧 과거 환율이다.
- 특정 날짜의 환율은 "그 날짜 이하에서 가장 최근 값"을 쓴다. 이 규칙으로 주말·공휴일도 함께 처리된다.
- 쓸 수 있는 값이 없으면(서비스 시작 이전 날짜, 아직 수집 안 된 통화) 사용자가 환율을 직접 입력하게 한다.
- API 키는 서버 환경변수로만 관리하고, 클라이언트는 `exchange_rates` 표만 읽는다.
- 화면 하단에 환율 출처를 표기한다.

## 4. 도메인 엔진 (`/lib/domain`)

순수 함수만 둔다. UI·DB·네트워크에 의존하지 않는다. 모든 금액은 `Money = { amountMinor: bigint, currency: string }`이다.

### 4.1 모듈

| 모듈 | 책임 |
|---|---|
| `currency` | ISO 4217 minor unit, 표시 자릿수 테이블 |
| `money` | Money 생성·덧셈·비교, 표시용 포맷 |
| `fixed` | 환율(10⁻¹⁰ 단위 bigint)·수수료율(10⁻⁶ 단위 bigint) 고정소수 연산, **단일 반올림** |
| `rate` | 지출 1건의 적용 환율 결정 (§4.2) |
| `split` | 원화 원가를 참여자 가중치로 분배 (§4.4) |
| `wallet` | 공금 원가 풀 시간순 재계산 (§4.3) |
| `balance` | 멤버별 순잔액 (§4.5) |
| `settle` | 그리디 송금 목록 (§4.6) |
| `display` | 송금 금액의 외화 환산 표시 (§4.7) |

**반올림 규칙**: half away from zero(0.5는 0에서 먼 쪽으로). 변환 1건마다 bigint 분자·분모로 계산하고, 마지막에 한 번만 반올림한다.

### 4.2 공금 외 지출의 원화 원가

지출 1건마다 `base_amount_minor`(원화 정수)를 확정한다. 우선순위:

1. **사용자가 이 지출에 직접 입력한 환율이 있으면**: 외화 × 입력 환율. 수수료는 적용하지 않는다(사용자가 실제 적용가를 입력한 것으로 본다).
2. **결제수단에 환율이 있으면**(현금 환전, 트래블카드 충전 환율): 외화 × 결제수단 환율 × (1 + 수수료율)
3. **그 외**(신용카드 등): 외화 × 지출 날짜의 API 환율 × (1 + 수수료율). 결제수단이 없으면 수수료율은 0이다.

- 저장 값: `base_amount_minor`, `rate_snapshot`, `fee_rate_snapshot`, `rate_source`('user' | 'funding_source' | 'api')
- 이 값들은 **이후 다시 계산하지 않는다**. 지출을 수정하면 수정 시점의 값으로 새로 확정하고, 이전 값은 `expense_history`에 남긴다.
- 지출 통화가 정산 통화(KRW)와 같으면 원가 = 금액이다.

### 4.3 공금 원가 풀

공금은 통화마다 두 개의 정수로 상태를 관리한다: `{ foreignMinor, costMinor }`.

공금 관련 이벤트(입금, 공금 지출)를 `(occurred_at, created_at, id)` 순서로 정렬해 처음부터 적용한다.

- **입금** (외화 c, 입금 원가 k): `foreignMinor += c`, `costMinor += k`
  - k(입금 원가)는 §4.2와 같은 우선순위로 정한다: 사용자가 입력한 환전 환율 → 입금에 연결한 결제수단의 환율 × (1 + 수수료율) (예: 시나리오 1의 D, 트래블카드 충전) → 입금 날짜의 API 환율. 정해진 값은 `contributions.base_amount_minor`에 스냅샷으로 저장한다.
- **공금 지출** (외화 s):
  - `foreignMinor ≥ s`일 때: 지출 원가 = round(`costMinor × s ÷ foreignMinor`). 그 원가를 `costMinor`에서, s를 `foreignMinor`에서 뺀다.
    - 잔액을 정확히 다 쓰면 원가는 `costMinor` 전부가 된다 (나눗셈 오차 없음).
  - `foreignMinor < s`(잔액 부족)일 때:
    - 남은 잔액 부분은 풀 원가 전부로 처리하고, 풀은 0이 된다(풀은 음수가 되지 않는다).
    - 초과분은 **부족분(deficit)**으로 따로 기록하고 지출 날짜의 API 환율로 임시 평가한다. 지출 통화가 정산 통화이면 액면가로 평가한다.
    - 이후 입금은 부족분부터 메운다. 메운 몫은 **그 입금의 실제 원가**로 해당 지출의 원가를 다시 정한다. 그래서 입금을 지출보다 늦게 기록해도 입금한 사람이 손해 보지 않는다. (2026-10-12 최종 리뷰 #1 반영)
    - 끝까지 메워지지 않은 부족분은 누가 대납했는지 엔진이 알 수 없다. 그래서 누구에게도 크레딧하지 않고 `unfunded`로 보고한다. 이때 Σ순잔액 = −Σunfunded이고, 정산(§4.6)은 거부된다. SP3에서는 "누가 대납했나"를 입력받아 입금으로 기록한 뒤 정산한다.
    - 화면에 "공금 잔액 부족 — 누군가 대납 중" 경고를 띄운다.
- **보존 법칙** (테스트로 검증): Σ입금 원가 = Σ공금 지출 원가 − Σ미충당 부족분 + 최종 `costMinor`
- 공금 지출의 원가는 저장하지 않는다(`base_amount_minor` = NULL). 과거 입금을 수정해도 합계가 항상 맞는다.

### 4.4 분배

- 분배 대상은 **원화 원가**이고, 가중치는 split_type에 따라 정한다.
  - `equal`: 참여자마다 1
  - `exact`: 참여자별 외화 금액. 합이 지출액과 같아야 하며, 다르면 입력 단계에서 거부한다.
  - `percent`: 참여자별 basis point. 합이 10000이어야 한다.
  - `shares`: 참여자별 정수 몫
- 각자 몫 = floor(원가 × 가중치 ÷ Σ가중치). 남는 원(나머지)은 1원씩 나눠 준다.
  - 나눠 주는 순서는 멤버 정렬 순서(`members.sort_order`, `id`)다.
  - **시작 위치는 `hash(expense_id) mod 참여자 수`**로 정한다. 결과는 매번 같고(결정적), 특정 멤버에게 나머지가 몰리지 않는다.
- 결과적으로 부담분 합 = 원가가 항상 정확히 성립한다.

### 4.5 순잔액

멤버 m의 순잔액(원화):

```
+ Σ m이 직접 결제한 지출의 원가
+ Σ m의 공금 입금 원가
− Σ m의 부담분 (공금 지출 + 개인 결제 지출 모두)
− 남은 공금 처리분
```

남은 공금(최종 `{foreignMinor, costMinor}`, 통화별)의 처리 방식은 정산할 때 고른다.

- **입금 비율대로 나눠 갖기** (기본값): 남은 원가를 각 멤버의 입금 원가 비율로 나눠서 각자 순잔액에서 뺀다. 외화 실물도 같은 비율로 나눈 금액을 보여준다(예: "남은 3,250엔 → A 813엔, B 812엔…"). 나머지 배분은 §4.4와 같은 규칙이다.
- **한 멤버가 전부 가져가기**: 가져가는 멤버의 순잔액에서 남은 원가 전부를 뺀다. 다른 멤버의 입금 원가 크레딧은 그대로 둔다.

**불변식** (테스트로 검증): Σ순잔액 = 0

### 4.6 정산 (그리디)

- 받을 사람(+)과 줄 사람(−)을 각각 금액 내림차순으로 정렬한다. 금액이 같으면 멤버 정렬 순서로 정한다.
- 매번 가장 많이 받을 사람과 가장 많이 줄 사람을 매칭해서 min(받을 금액, 줄 금액)만큼 송금하도록 정하고, 0이 될 때까지 반복한다.
- 결과: `[{ from, to, amountMinor(KRW) }]`
- 서버에서 결과를 만든 뒤 다시 검산한다(송금을 반영하면 모든 순잔액이 0이 되는지). 실패하면 결과를 보여주지 않고 오류를 기록한다.

### 4.7 외화 표시

송금 금액마다 주 통화로 두 가지 환산값을 보여준다(표시 자릿수로 반올림).
- **여행 평균 환율**: 이 여행의 주 통화 지출 원가 합 ÷ 외화 합(공금 지출 포함). 주 통화 지출이 없으면 공금 평균 원가를 쓰고, 그것도 없으면 이 항목을 표시하지 않는다.
- **오늘 환율**: `exchange_rates`에서 오늘 이하 가장 최근 값

정산 시점의 두 환율 값은 `settlements`에 저장한다. 나중에 다시 열어도 같은 숫자가 나온다.

  - 변경: `rate_to_base` 대신 `base_amount_minor bigint`를 저장한다 (입금 원가 스냅샷)
- `expenses`
  - 추가: `base_amount_minor bigint null`(공금 지출이면 NULL), `fee_rate_snapshot numeric(8,6)`
  - `rate_snapshot`은 공금 지출이면 NULL
  - CHECK: `paid_by_member_id`와 `paid_by_wallet_id` 중 정확히 하나만 NOT NULL
- `expense_participants`, `expense_history`: 원본 그대로
- 신규 `exchange_rates`: `date`, `currency`, `rate_to_krw numeric(20,10)`, `source`, PK(date, currency)
- 신규 `settlements`: `trip_id`, `leftover_policy`('split_by_contribution' | 'taker'), `taker_member_id`, `avg_rate`, `today_rate`, `result jsonb`, `created_by`, `created_at`
- 마이그레이션: Supabase CLI(`supabase/migrations`)

### 5.1 참여와 권한

- 모든 사용자는 Supabase **익명 로그인**으로 시작한다(Turnstile 캡차 사용).
- 여행 생성자는 여행을 만들 때 자기 멤버(admin)와 `member_devices`가 함께 만들어진다.
- 입장은 `join_trip(invite_code, member_id)` RPC(SECURITY DEFINER)로만 한다.
  - 초대 코드를 확인하고 `member_devices`에 (member_id, auth.uid())를 넣는다.
  - 이미 다른 기기가 연결된 멤버여도 허용하고, 화면에 "다른 기기에서도 사용 중"이라고 표시한다.
  - 사용자별 횟수 제한: 10분에 10회. 초대 코드 무작위 대입을 막기 위함이다.
- 멤버 목록 미리보기(이름만)는 `trip_preview(invite_code)` RPC로 제공한다. 초대 코드를 아는 사람만 볼 수 있다.
- **RLS**: 모든 여행 하위 테이블은 `member_devices`에 (해당 여행의 멤버, auth.uid())가 있을 때만 읽기·쓰기를 허용한다.
  - `is_finalized = true`이면 쓰기는 admin만 할 수 있다.
  - `exchange_rates`는 모두 읽기만 가능하고, 쓰기는 서버(service role)만 한다.

### 5.2 쓰기 경로

- 지출·입금 저장: 클라이언트가 도메인 엔진으로 원가를 계산해서 Supabase에 직접 쓴다(RLS 적용).
  - 같은 여행 멤버끼리는 서로 신뢰하는 구조다.
  - 서버는 정산할 때 원가 스냅샷을 다시 계산하지 않고, 공금·분배·순잔액·정산만 다시 계산한다.
- 정산: Next.js Route Handler가 사용자 세션으로 데이터를 읽고, 도메인 엔진으로 계산·검산한 뒤 `settlements`에 저장한다.
- 수정: 지출을 수정할 때마다 트리거가 이전 값과 새 값을 `expense_history`에 기록한다.

### SP1. 도메인 엔진

- §4의 모듈 전체
- 테스트
  - 원본 명세 §8의 단위 케이스 6개
  - §12 시나리오 3개를 픽스처로
  - 속성 테스트: Σ순잔액 = 0 / 같은 입력이면 같은 결과 / 공금 원가 보존 / 분배 합 = 원가
- **완료 기준**: 테스트 전부 통과. 시나리오 1의 정산 결과를 사람이 손으로 검산한 값과 비교해 문서(`docs/scenarios.md`)로 남긴다.

### SP2. 여행·지출 앱

- 화면: 랜딩 / 여행 만들기 / 초대 링크 공유 / 입장·멤버 선택 / 여행 홈(지출·공금 탭) / 지출 입력 시트 / 결제수단 / 공금 입금

### SP3. 정산과 공개 준비
- 정산 탭: 남은 공금 처리 선택, 송금 목록(원화 + 외화 2종), 확정 잠금

- **완료 기준**: 공개 URL에서 성공 기준 1~6 전부 확인. Playwright E2E(모바일 화면 크기) 통과.

## 7. 화면 (SP2·SP3)

- **랜딩**: 서비스 소개 + "여행 만들기"
- **여행 만들기**: 이름, 날짜, 통화(여러 개, 첫 번째가 주 통화), 멤버 이름 목록. 정산 통화는 KRW 고정(MVP).
- **초대 링크**: `/j/{code}`. Web Share API로 공유하고, 지원하지 않으면 링크 복사.
- **입장**: "나는 누구인가요?" 멤버 목록 → 선택 → 여행 홈
- **여행 홈**: 탭 [지출 / 공금 / 정산]. 상단에 통화별 공금 잔액과 내 부담 합계(원화).
- **지출 입력 (하단 시트)**
  - 기본: 금액(숫자 키패드) → 통화(주 통화가 먼저 선택됨) → 누가 냈나(공금 / 멤버) → 참여자(기본 전체) → 저장
  - 상세(접힘): 결제수단, 분배 방식, 카테고리, 메모, 날짜, 환율 직접 입력
  - 저장 전 미리보기: "≈ 45,250원 · 결제수단 환율 905원/엔"처럼 원화 금액과 환율 출처
- **결제수단**: 멤버별로 종류, 통화, 환율(선택), 수수료율(선택), 이름
- **공금**: 입금 목록·추가, 통화별 잔액, 평균 원가, 음수 경고
- **정산 (admin)**: 남은 공금 처리 선택 → 송금 목록. 각 줄 형식: "A → B 32,500원 · 평균 환율 ≈ 3,580엔 · 오늘 환율 ≈ 3,540엔". 그 아래 공유 이미지·텍스트 복사, 확정 버튼.
- **혼자 여행 (멤버 1명)**: 정산 탭 대신 요약(총 지출, 카테고리별, 통화별)

## 8. 남용 방지·개인정보·운영

- 익명 로그인에 Cloudflare Turnstile을 쓴다(Supabase Auth 기본 지원).
- 쓰기 횟수 제한은 Postgres 트리거로 건다(별도 서비스 없음).
  - 여행 생성: 사용자당 하루 20개
  - 지출·입금: 사용자당 분당 60건
- 개인정보 처리방침 페이지
  - 수집: 표시 이름, 지출 메모·금액, 익명 사용자 ID
  - 계좌·연락처는 수집하지 않는다
- admin은 여행을 삭제할 수 있다. 마지막 활동 후 1년이 지난 여행은 Cron이 자동 삭제한다.
- 출처 표기: 환율 공급자(ExchangeRate-API 등)
- 비밀값(수출입은행 키, Supabase service role, Turnstile secret)은 Vercel 환경변수로 관리한다. 클라이언트에는 Supabase anon key와 Turnstile site key만 노출한다.

## 9. 에러 처리

| 상황 | 처리 |
|---|---|
| 지출 날짜의 API 환율 없음 | 그 날짜 이하 가장 최근 값 사용. 그것도 없으면 환율 직접 입력을 요구하고 "임시 환율" 배지 |
| 환율 수집 Cron 실패 | 기존 값 유지, 다음 날 재시도. 연속 3일 실패하면 로그 경고 |
| 공금 잔액 음수 | 공금 탭·여행 홈에 경고 배너 (§4.3) |
| exact/percent 합 불일치 | 저장 버튼 비활성화 + 차이 금액 표시 |
| 정산 검산 실패 | 결과를 보여주지 않고 오류 화면 + 서버 로그 (구조상 발생하지 않아야 함) |
| 확정된 여행에 쓰기 시도(비admin) | RLS가 거부하고, UI에 "확정된 여행입니다" 표시 |
| 초대 코드 오류·횟수 제한 초과 | "링크를 다시 확인해 주세요" / "잠시 후 다시 시도해 주세요" |

## 10. 테스트 전략

- **도메인 (Vitest, 테스트 우선)**: §6 SP1 목록. 금액 연산에 float가 섞이지 않았는지 ESLint 규칙과 타입으로 막는다.
- **RLS**: 로컬 Supabase(`supabase start`)에서 익명 사용자 두 명으로 다음을 확인한다.
  - 다른 여행 읽기·쓰기 거부
  - 확정 후 비admin 쓰기 거부
  - `join_trip` 횟수 제한
- **E2E (Playwright, 모바일 화면 크기)**: 여행 생성 → 두 번째 브라우저 컨텍스트로 입장 → 지출 3건(공금 1, 개인 2) + 입금 2건 → 정산 → 결과 금액 확인
- **검증 시나리오**: 원본 명세 §12의 3개를 SP1 픽스처로 고정한다. SP3 E2E에서 시나리오 1을 화면으로 다시 확인한다.
